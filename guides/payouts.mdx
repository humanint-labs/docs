[`POST /v1/transactions/payout`](/api-reference) creates a payout routed through your connected providers. Capisum uses one canonical `destination` shape; required fields depend on the resolved **provider + country + currency + rail**. For accepting money, see [Pay-in integration](/guides/pay-ins).

## Go-live checklist

Complete these steps before processing real payouts in production:

<Steps>
  <Step title="Test in sandbox">
    Connect providers with sandbox credentials and run the [Quickstart](/quickstart). Confirm payouts reach `completed` and [webhooks](/guides/webhooks) verify correctly.
  </Step>
  <Step title="Discover usable rails">
    Call [`GET /v1/payouts/capabilities`](/api-reference). The response includes only providers connected in your current environment, with per-rail `required_fields`.
  </Step>
  <Step title="Connect live providers">
    Switch the dashboard to **Live** and connect each provider with production API credentials. For Paystack, [disable Transfer OTP](/guides/providers#disable-transfer-otp) in the Paystack Dashboard (required for payouts; account-wide, including test).
  </Step>
  <Step title="Create a production API key">
    Generate a production key in [API keys](https://app.capisum.com/api-keys). Store it server-side only.
  </Step>
  <Step title="Register your webhook URL">
    Add a production endpoint at [Webhooks → Configuration](https://app.capisum.com/webhooks/config). Save the signing secret securely.
  </Step>
  <Step title="Verify beneficiary accounts">
    Call [`POST /v1/verify/account`](/guides/account-verification) before your first live payout when the corridor supports name resolution.
  </Step>
  <Step title="Start with a small payout">
    Send a low-value transfer to validate end-to-end routing, then scale volume gradually.
  </Step>
</Steps>

See [Providers](/guides/providers) for per-provider capabilities.

## Discover capabilities first

```bash
curl -s "$CAPISUM_BASE_URL/v1/payouts/capabilities" \
  -H "Authorization: Bearer $CAPISUM_API_KEY"
```

The response is scoped to **your connected providers** in the current environment. Each provider entry includes `rails[]` with:

| Field | Meaning |
| --- | --- |
| `rail` | Network id (`bank_transfer`, `ach`, `sepa`, `pix`, `spei`, `mobile_money`, `crypto`) |
| `currency` / `country` | Corridor |
| `destinations` | Capisum channel types (`bank_account`, `mobile_money`, `crypto_wallet`) |
| `required_fields` | Fields Capisum expects on `destination` (e.g. `recipient.name`, `routing_number`) |

Do not hardcode a global currency list — capabilities are the source of truth.

## Amounts

All amounts are in **minor units** (the smallest currency unit):

| Currency | Minor unit | Example |
| --- | --- | --- |
| NGN | Kobo | `500000` = ₦5,000.00 |
| USD | Cent | `25000` = $250.00 |
| GHS | Pesewa | `10000` = GH₵100.00 |
| KES | Cent | `50000` = KSh500.00 |
| USDT / BTC / ETH / SOL / XLM | 8 decimals | `500000000` = 5 USDT; `40000000` = 0.4 BTC |

Pass `amount` as a string or integer. Capisum stores and returns amounts as integers.

## Destination contract

### Shape

```json
{
  "type": "bank_account",
  "country": "US",
  "rail": "ach",
  "recipient": {
    "type": "individual",
    "name": "Alex Smith",
    "email": "alex@example.com",
    "physical_address": "123 Main Street, New York"
  },
  "account_number": "123456789",
  "routing_number": "021000021",
  "account_type": "checking",
  "account_name": "Alex Smith"
}
```

| Field | Required | Description |
| --- | --- | --- |
| `type` | Recommended | `bank_account`, `mobile_money`, or `crypto_wallet` |
| `rail` | When ambiguous | Capisum payout rail. **Inferred** when only one rail matches the resolved provider + country + currency (+ type). If multiple match and none is supplied, Capisum returns `PAYOUT_RAIL_REQUIRED`. |
| `country` | When multi-country | ISO 3166-1 alpha-2. Defaults from the currency corridor when unambiguous. |
| `recipient` | When the rail requires it | Beneficiary profile: `type` (`individual` \| `business`), `name`, `email`, `physical_address`. Only required when `required_fields` lists `recipient.*`. |
| `account_number` | Bank / mobile money | Account, CLABE, CCI, or wallet number |
| `address` + `network` | Crypto | Wallet address and chain (`trc20`, `erc20`, …) |
| `bank_id` | Many NGN rails | Capisum canonical id from [`GET /v1/reference/banks`](/api-reference) |
| Bank / rail fields | Per rail | e.g. `routing_number`, `account_type`, `iban`, `bic`, `pix_key`, `mobile_money_code` |

<Info>
  Flat legacy profile fields (`name`, `email`, `physical_address`, `recipient_type` at the top level of `destination`) are still accepted and lifted into `destination.recipient`. Prefer the nested shape.
</Info>

<Warning>
  Do not invent placeholder emails or addresses. If a rail lists `recipient.email` / `recipient.physical_address`, send real beneficiary data.
</Warning>

### Rails vs type

- **`type`** — Capisum channel (`bank_account` / `mobile_money` / `crypto_wallet`)
- **`rail`** — payment network (`ach`, `sepa`, `pix`, `bank_transfer`, …)

Example: Yativo USD uses `type: bank_account` and `rail: ach`. Fincra GHS MoMo uses `type: mobile_money` and `rail: mobile_money` (usually inferred from `type`).

## Provider routing

Set `provider` to route explicitly, or omit it so Capisum applies your dashboard routing defaults/rules. Validation always runs against the **resolved** provider + country + currency + rail.

## Transaction lifecycle

Payout creation returns immediately with `status: queued`. Capisum submits the payout to the provider asynchronously.

| Status | Meaning |
| --- | --- |
| `queued` | Accepted; waiting for worker submission |
| `processing` | Provider submission in progress |
| `pending_provider_confirmation` | Submitted to provider; awaiting webhook or confirmation poll |
| `uncertain` | Provider outcome unclear (timeout or ambiguous response) |
| `manual_review` | Needs attention; eligible for dashboard retry after failed attempt |
| `completed` / `settled` | Payout succeeded |
| `failed` | Terminal failure |
| `refunded` | Provider reversed the transfer |
| `cancelled` | Cancelled before settlement |

Prefer [webhooks](/guides/webhooks) for terminal status updates. Use verify as a fallback:

- `GET /v1/transactions/{id}` or `GET /v1/transactions/ref/{reference}` — read current status
- `POST /v1/transactions/{id}/verify` — ask the provider for the latest status
